KubeFoundation-基于FoundationDB构建Etcd兼容层

13eholder
2026-11-08 (Updated: 2026-11-08)
分布式系统
FoundationDB, Kubernetes, etcd, 分布式存储

在本系列中，我们将基于开源的工业级强一致性分布式KV存储引擎FoundationDB构建一个Etcd兼容层，用于无缝替换K8S的默认状态存储后端Etcd从而拓展K8S集群的承载范围，突破原有的限制。
大概会按照：Etcd瓶颈分析、已有方案调研、Etcd-K8S api subset分析、FoundationDB特性介绍、项目架构设计、测试与数据分析的顺序写完整个系列。顺便穿插一些etcd与tinykv的设计分析、源码分析。如果还有时间，再写点FoundationDB。
目前的Go原型代码已经通过K8S sunobuoy完整性测试且在性能测试。但是，我要把它改造成Rust，这还需要一点小小的时间。
别问，问就是，我爱原神。

一些小的前言

项目的起因很简单，今年4月的时候，某云的一个Agent团队通过合作专家对齐到我们实验室，说它们云端集群已经遭遇了很明显的存储瓶颈，按照目前的增长速度来看，等到明年Etcd就要彻底承受不住了。
他们的集群有2K节点、每节点大约20~30 POD；一个滚动更新会下发数万更新请求，导致Etcd存储限额迅速触及上限(4GB)从而停止服务。
即使他们已经将Event/Lease以及其他高频资源都拆分出来，每资源一个单独的Etcd集群，并且放弃持久性，将Etcd部署到tmpfs上换取性能(每天低谷期用脚本手动备份存储文件)，Etcd还是很难抗住 频繁变更的集群。
现在的问题是拆无可拆，在集群规模进一步扩大的情况下(最低目标是2W节点，最高是对齐国际前沿水平)，即使是一个小的级联请求也可能导致Etcd服务降级(无法满足SLA)，甚至暂停写入。

我们老板的初始拍皮鼓方案是：“咱们实验室的入门考核项目是TinyKV,大家都懂Multiple-Raft,我们来改造Etcd成为一个Multiple-Raft集群从而突破瓶颈”。
好吧，我没有想到，在2026的今天，还有人想要造一个Multiple-Raft KV，还要生产高可用。不是，爷们，即使有LLM，你也别拿我当许愿机啊。
在做完单节点Etcd内存化设计(反正都部署到tmpfs了，不如改造磁盘B+树为内存B+树)的优化之后，经过漫长的探索和测试，老板终于相信，验证一个Multiple-Raft KV的高可用性是一个漫长且折磨的过程，而且需要大量的生产测试。我们没有这个时间，合作方也不会给这个时间。再加上手下的学弟都跑去干LLM了，这个方案就给我拿来当毕业设计了，我正好从头搓一搓。
冷静下来后发现，一个可行的方向是基于已有的存储构造兼容层，从而突破存储瓶颈。最终选择基于FoundationDB来构建兼容层(很早就有社区讨论，性能好+接口简单易用)。

K8S与Etcd

借用一下Houston, we have a problem with etcd 演讲中的图片说明K8S和Etcd的工作流。

K8S的核心工作模式是 声明式API+控制循环，即$\text{Watch} \rightarrow \text{Reconcile} \rightarrow \text{Write Back}$。

  • 控制器、调度器、容器管理等进程将命令(增删改查一个KV)传递给API-Server，API-Server将命令转换为Etcd API传递给Etcd并获取结果再传回。显然，API-Server & Etcd单点提供所有的读写服务，压力巨大，因此采用subcribe + publish的模式，由etcd主动推送更改到API-Server的Watch Cache，API-Server再主动推送给订阅了更改的其他组件，从而减少两者的读压力。
  • 控制器、调度器、容器管理等会持续比较期望状态和目前状态是否一致，不一致则会做一些操作(下载容器，运行容器，创建关联对象等)，并在这个过程中持续更新存储在etcd中的对象。以创建一个POD为例，会经历创建Deployment -> StatefulSet -> Pod，每个对象还会多次更新状态(Start/Paused/Running/Ready等)或者加运行注释等。一条客户端命令对应十几次、几十次的etcd txn，反复更改同一个etcd对象的部分字段。

K8S节点存活状态依赖etcd租约机制，只要集群运行就会有大量的背景写入。

一句话，K8S的负载是写多读少，主动推送，而且具有明显的周期性，或者说突发压力(创建、滚动更新、删除等)。
K8S如何使用etcd api我们后续再详细讲，先来跑一跑测试，看看etcd到底能承受多少的k8s节点。

Etcd性能分析

理论分析

etcd是基于Raft共识算法的强一致性KV存储，通常采用三节点部署，拓展etcd的节点数量无法提升写入性能和存储限额。更糟糕的是，由于底层磁盘存储引擎使用bbolt(单写多读B+树，4KB磁盘页)，详情见((8 封私信) bbolt源码分析 - 知乎)，随着磁盘用量的增长，写入性能会指数级下降(由于Copy-On-Write写入放大和事务管理机制)。

根据etcd简要写入流程图分析潜在的瓶颈：

  1. propose阶段： leader节点需要写入Entry到磁盘WAL并通过网络将日志传输到从节点；从节点同样需要持久化日志。简单估算就是 一次 SSD Write + SSD Fsync + Network RTT。
  2. apply阶段：将多个etcd txn对应的KV更改聚合为一个bbolt txn写入到磁盘B+树。对应多个磁盘页的写入(4KB)和一次fsync

etcd官方给出的核心观测指标有:

  • etcd_disk_wal_fsync_duration_seconds_bucket WAL 刷盘耗时分布。
    • 标准：P99 必须 < 10ms（越接近 1ms 性能越好）
  • etcd_disk_backend_commit_duration_seconds_bucket 底层 bbolt 将事务提交到磁盘的耗时。
    • 标准：P99 必须 < 25ms。
  • etcd_network_peer_round_trip_time_seconds_bucket 三节点间 Raft 通信的端到端 RTT。
    • 标准：99% 的网络包必须在 < 5ms 内返回。
  • etcd_server_leader_changes_seen_total Leader 发生切换的次数。
    • 标准：在稳定集群中该值应当长期为 0。若频繁自增，说明网络延迟超标或磁盘卡顿丢掉了心跳。

后端提交延迟目前看来最为重要，因为一次缓慢的提交既会导致后续的批量写入排队等待时间激增，还会导致内存缓存用量激增进而影响到读性能(bbolt使用mmap全量映射磁盘页，系统换出内存页)
etcd批量提交事务有两个触发参数，一个是100ms的提交间隔，另一个是10000个Txn Op，通常触发的是时间参数。

单节点性能测试

单节点性能指标如下图所示：

  1. etcd适合处理小KV,etcd官方推荐 KeySize < 1KB, ValueSize < 10KB。当KV尺寸大了之后，物化开销，内存开销，排队延迟，提交延迟都会激增。 很遗憾，K8s做不到存储小KV。
  2. 串行单写模式上限低，即使增加客户端并发度，充分利用批处理机制，单机下能够承载的事务也不过1s 5W. 当k8s集群节点数增多时，仅维护集群存在需要的租约写入开销都足够etcd喝一壶。更不要说滚动更新、级联更新这样的地狱场景。
  3. 14.2K异常是因为外部测试+磁盘抖动引起的，不是etcd原因

  2. put/commit 数量是一个bbolt事务聚合提交的etcd entry 数量, batch是有效的，一般在2000并发的时候聚合效果最好(bbolt写入分两阶段 update和commit。update阶段是内存中的物化缓存，对应一个KV在内存中被拆分为多个4KB页面)，随着Value的增大，Update阶段耗时增多，从而影响聚合效率。
  3. commit 均时分为两部分： B+树结构的调整(split/rebalance)和磁盘页COW写入(write耗时)；由于bbolt底层采用4KB磁盘页+COW，value越大，调整树结构和写入需要的时间就越多。
  4. TxnSrv是收到GRPC请求，到完成请求返回响应的全时间。单节点测试下，不涉及网络就存在如此糟糕的性能，并且耗时与commit均时相差甚远，大胆推测，时间大概率消耗在了等待bbolt事务串行提交上。

性能分析

此处简单分析一下2k node, 40k pod, pod size 分别为 4kb和20kb的小集群性能测试数据(k8s操作与etcd api如何交互，下期再讨论)，大规模集群的性能分析之后再写。这里就不上grafana图了。
目前的问题是，在滚动更新阶段，由于写操作积压导致read index操作缓慢，进而影响单点操作(常见的访问模式是CAS，即读取当前最新的数据，比较，然后执行操作，所以读延迟至关重要)

要点：

  • 4KB：单点动词只有 DELETE 到 ~1s，GET/POST/PATCH 均 ≤95ms。DELETE 的 ~940ms 缺口与其内嵌 quorum GET 一致，删除先读后写，读在写积压尖峰上等 ReadIndex（get op 阶段 exact 97ms，但 5m 窗 p99 max 冲到 976ms，与 DELETE 尾部同时刻）。
  • 20KB：全动词塌到 ~0.95–0.99s——get/create/update/delete 全部钉在[0.8,1.0]s 桶内，读写同源饱和（raft 管线），不再是 4KB 的”只有 DELETE”。写（create 935 / update 971ms）与读（get 990ms）几乎无差，说明 commit 管线整体成为单一点。
  • 20KB DELETE 4.23s 与 list 4.96s 钉在 5s 桶边——删除路径（KWOK 30s drain + 删除风暴）在 20KB 下劣化最重。

更要命的是磁盘占用，etcd采用MVCC+5分钟周期性压缩(分多个批次，防止影响正常写入)，短期突发的巨量请求很容易将限额打满从而暂停写入服务。常见的存储限额是8GB，超过8GB后由于磁盘碎片限制性能会出现下降。

20KB Pod Size快将限额打满了

小结

etcd实际能承载的节点数量+资源数量，既取决于KV大小，也取决于资源的变更频率(启动阶段性能优于滚动更新)。线性一致性下，raft串行写积压会导致读性能下降，进而影响符合操作的性能。目前看来，存储的瓶颈在于串行写入以及读写无法分离。（集群再大一些，如5W，网络更可能先到瓶颈）。
但是无论怎么讲， 2k节点就将etcd逼到极限，和客户的数据、需求对上了，问题确实存在，可以往后做了。

etcd性能优化

Houston, we have a problem with etcd 中说的很清楚：

  1. 使用k8s参数 --etcd-servers-overrides=<group/resource>#<etcd-endpoint-1>;<etcd-endpoint-2>...将特定资源拆分到专用etcd集群。 面临的问题是，集群数量大了之后，一类资源的空间占用轻松逼近etcd quota
  2. 在现有存储上构建兼容层(AWS/Google/字节)
  3. 优化etcd,但收益有限，架构瓶颈不可避免。

个人认为启发最大的是：Running k8s-1m 和突破 etcd 限制！字节开源自研 K8s 存储 KubeBrain - InfoQ
字节的做法说明了无论如何，生产环境需要支持2W+节点，一定要突破单Raft组限制，修修补补的极限就在这里。
